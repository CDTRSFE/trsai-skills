# 错误码处置

脚本失败时按 `error_code` 说明原因并转述返回体里的 `hint`。**不要把原始 JSON 直接甩给用户**，除非用户明确要求。

## 目录

- 一、通用错误码
- 二、`CONFIG_ERROR` 要先分清是配置问题还是参数问题
- 三、`update` 专用错误码
- 四、退出码的含义

---

## 一、通用错误码

| 错误码 | 含义 | 怎么办 |
|---|---|---|
| `AUTH_FAILED` | 用户名或密码错 | 去 Jira 网页确认能登录。脚本不会重试 |
| `CAPTCHA_LOCKED` | 账号被 Jira 验证码保护锁定 | **立即停手不要重试**，越试锁越久。必须用浏览器登录该账号一次才能解除 |
| `PERMISSION_DENIED` | 账号无权限 | 确认项目或操作权限 |
| `NOT_FOUND` | issue 不存在或无查看权限 | Jira 对无权限的 issue 也返回 404，两种情况分不开 |
| `JQL_INVALID` | JQL 被 Jira 拒绝 | 见下方专条 |
| `RATE_LIMITED` | 限流且重试一次后仍失败 | 降频后再试 |
| `UNEXPECTED_RESPONSE` | 返回的不是 JSON（常是登录页或反向代理拦截） | 错误里回带了响应前 200 字符，一眼可辨 |
| `SSL_ERROR` | 证书校验失败 | 自签名证书的源把 `insecure` 设为 `true` |
| `NETWORK_ERROR` | 连不上或超时 | 先查网络。**不要因此改用另一个源** |
| `WATCH_JQL_CHANGED` | 监控名绑定了别的 JQL | 确认要换就加 `--reset` |
| `PLAN_REJECTED` | plan 过期、已用过或不存在 | 重新预览，不要重试同一个 plan |
| `PREVIEW_REQIRED`（实际码为 `PREVIEW_REQUIRED`） | 写操作没带 `--preview` | 见下方专条 |

**`JQL_INVALID` 的两种语境**

查询语境：按回带的 Jira 报错原文修正 JQL。若报错形如「域中没有该值」且涉及状态名，换成英文原始名或状态 id **重试一次（最多一次）**；再失败就把 Jira 原文报给用户，不要反复试。状态名的写法规则见 `命令速查.md` 的查询纪律第 2 条。

`update` 语境：这个码的含义是「请求被 Jira 拒绝」，**不要去改 JQL**。update 全程不发 JQL 查询条件，客户端只是把所有 HTTP 400 统一归到了这个码上。此时看 `error` 里的 Jira 原文（多半是字段值不合法或无权限），别浪费回合去改一条根本不存在的 JQL。

**`PREVIEW_REQUIRED` 是正常拦截，不是故障**

它说明必须先出预览、等用户确认，然后用 `apply --plan-id` 执行。**不得改用别的方式绕过**：不许直接调接口、不许用遗留脚本、不许把两步串成一条命令。

## 二、`CONFIG_ERROR` 要先分清是配置问题还是参数问题

两者处置**完全相反**，分错了会把一份本来正确的配置改坏。

**真的是配置问题**：配置文件不存在、不是合法 JSON、缺 `sources` 数组、某个源缺 `base_url` / `username` / `password`、有多个源却没写 `default_source`、找不到 `--source` 指定的源名。

→ 指向工程根 `jira_config.json`，对照模板 `jira_config.example.json` 说明缺什么。**不要自己造一个临时配置、不要反复重试。**

其中「找不到 `--source` 指定的源名」最常见的成因是源名没有逐字符对上——比较是大小写敏感的，也不会去掉前后空格。

**其实是参数问题**：`--field` 没写成 `k=v` 形式、`--description-file` 路径读不到、`count-by --group-by fixVersion` 但 JQL 里没有 `project = KEY`。

→ **改参数重试即可，绝对不要去动配置文件。**

## 三、`update` 专用错误码

下面这些退出码为 2 的都是本地参数校验，**一次网络请求都没发出去**，改参数重试即可，绝对不要去动配置文件。

| 错误码 | 退出码 | 含义与处置 |
|---|---|---|
| `FIELD_NOT_ALLOWED` | 2 | `--set` 的键不在七字段白名单内。四种情况：写了 `customfield_xxx` 之类白名单外字段（直接放弃这个字段）、写了中文名（按 `hint` 换成英文名）、写了 `status` 或 `状态`（改用 `--status`）、写了 `description`（改用 `--description-file`） |
| `FIELD_VALUE_INVALID` | 2 | 值本身不合法。常见：`--set summary=2026` 被当成整数解析、`--set labels=abc` 没写成数组、直接塞了接口请求体、同一字段给了两次、标签含空格、对不可清空的字段传 `null`、`--description-file` 内容为空（描述不支持清空，要清空请让用户在 Jira 网页操作）。按 `hint` 改写值重试 |
| `INVALID_DATE_EXPRESSION` | 2 | 日期说法不在封闭词表内，或写了已经过去的「本周某」。**改用绝对日期 `YYYY-MM-DD`**，不要自己顺延到下周 |
| `INVALID_ISSUE_KEY` | 2 | 单号格式不对（归一化后仍不匹配 `[A-Z][A-Z0-9_]*-数字`）。让用户确认单号，不要猜 |
| `EMPTY_CHANGESET` | 2 | 既没给任何 `--set` / `--description-file`，也没给 `--status`。至少给一项改动 |
| `BATCH_LIMIT_EXCEEDED` | 2 | 去重后超过 50 条。先把筛选条件收窄，别拆成多批硬冲 |
| `BATCH_ASSERTION_REQUIRED` | 2 | 两条及以上却没带 `--complete-set`。**补这个开关之前先自查：上一步查询有没有 `truncated: true`**，有就先收窄条件，别无脑补开关 |
| `BATCH_BODY_FIELD_FORBIDDEN` | 2 | 多条单里出现了 `--set summary=` 或 `--description-file`。标题和描述是覆盖式写入、写错即原文丢失，只允许单条改，拆成一条一条来 |
| `CROSS_PROJECT_VERSION_FORBIDDEN` | 2 | `--set fixVersions=` 的单号跨了多个项目前缀。同名版本在每个项目下是不同的内部 id，**按项目分批改**。其余字段跨项目批量是允许的 |
| `WRITE_SOURCE_NOT_ALLOWED` | 2 | 目标源不在可写清单里。这条限制是临时的，详见 `更新操作规则.md` 第六节。如实说明并停下，**不要改配置、不要换源重试** |
| `FIELD_VALUE_NO_MATCH` / `FIELD_VALUE_AMBIGUOUS` | 1 | 经办人／优先级／修复版本按名字查不到，或查到多个。返回体里带 `field` 与 `candidates`：**把候选列给用户让他挑，绝不自己猜一个**；无候选就让用户确认准确名字。此时预览未落地，选定后重跑一次预览即可 |
| `PREVIEW_HAS_BLOCKERS` | 1 | 有条目过不了预览：目标状态不在该单类型的状态集合内、按寻路规则走不到、已是完成类状态却没带 `--allow-closed-transition`、项目下没有指定的修复版本。**整份预览失败、不生成 plan、全有全无**，没有「跳过这几条、剩下的照做」这一档。返回体里逐条给了原因与该单可走的目标状态，还给了一条剔除问题条目后可原样执行的完整命令行——把原因贴给用户，由用户决定是照那条命令只改剩下的，还是换个目标状态 |
| `PLAN_MALFORMED` | 1 | `apply` 时发现 plan 结构缺字段。重新走一次 `update --preview`，**不要试图手改 `state/plans` 下的文件** |

## 四、退出码的含义

- `0` 成功
- `1` 业务失败
- `2` 配置或参数错误

注意一个例外：`apply` 整批跑完退出码恒为 0、`ok` 恒为 `true`，**退出码 0 不等于逐条全部成功**。逐条成败只看返回体里的 `counts` 与 `has_failures`。
