# 更新操作规则

`create`（建单）与 `update`（改已有单）都会真正写进 Jira，且**本工具不提供撤销**。改错了只能人工按审计记录往回补。

执行这两个子命令之前必须读完本文。`SKILL.md` 的《全局安全边界》只留了几条最要命的，细则全在这里。

## 目录

- 一、两阶段确认流程（一步都不能省）

## 一、两阶段确认流程（一步都不能省）

1. 跑 `<子命令> --preview`。命令行只读不写，返回 `plan_id` 与预览文本。
2. **把预览文本原样整段贴给用户**，等用户明确说确认。
3. 用户确认后跑 `apply --plan-id <上一步的 plan_id>`。
4. **把执行结果文本原样整段贴给用户。**

绝不自己把第 1 步和第 3 步连着跑完。

`apply` 不接受 `--source`——它的目标源在生成预览时就写进 plan 文件锁死了，当次传 `--source` 不生效，传了反而会造出「命令行写着甲源、实际打到乙源」的假象。

**plan 的有效期分档、且一律一次性消费**：`create` 与单条 `update` 是 5 分钟，批量 `update`（去重后两条及以上）是 15 分钟。实际值以返回体里的 `ttl_seconds` / `expires_at` 为准，不要凭记忆统一报成 5 分钟。过期或已消费的 plan 再 `apply` 会被拒（`PLAN_REJECTED`），此时重新预览，不要重试同一个 plan。

## 二、`create` 建单

```bash
# 第一阶段：生成预览（不会写入 Jira）
python3 <工程根>/scripts/jira_cli.py --source <源名> create \
  --project TRS --type 任务 --summary "标题" \
  --description-file /tmp/desc.md --description-format md \
  --field labels=test --preview

# 第二阶段：用户明确确认后执行（不带 --source）
python3 <工程根>/scripts/jira_cli.py apply --plan-id plan_xxxxxxxx
```

- 预览要展示给用户的内容：项目、类型、标题、描述、自定义字段。按《选哪个 Jira 源》的要求，预览**第一行**还要写 `目标源：源名（业务标签）`。
- **子任务创建**：直接传 `--parent <父单KEY>`（如 `--parent XMKFB-12099`），脚本会自动推导项目 key 并将类型设为「子任务」；若需要也可显式传 `--type 子任务`。
- 不确定必填字段时先用 `createmeta` 查。必填缺失脚本会直接报错，**不要编造占位内容去填**。
- 描述是 Jira wiki 标记不是 Markdown。给 Markdown 文件时用 `--description-format md`（默认）让脚本转换，已经是 wiki 格式才用 `wiki`。
- 支持全生命周期操作：除了建单与改单，还提供评论（`comment`）、经办人分配（`assign`）、关联（`link`）、工时（`worklog`）、附件（`attach`）以及受控删除（`delete`），全部遵循两阶段确认。

**建单用 `--field`，改单用 `--set`，两个参数名不可混用**：`create` 只认 `--field`，`update` 只认 `--set`，写反了参数解析器直接报未知参数。两者的 `k=v` 解析语义完全相同，但名字是定死的，别按记忆串写。

- 建单：`--field labels=test`
- 改单：`--set labels='["test"]'`

## 三、`update` 改单：能改哪些字段

`update` 改的是**已经存在**的单，能改七个核心字段（`--set`）外加状态（`--status`，走流转接口）及自定义字段（`customfield_*`）：

截止日期、经办人、优先级、修复版本、标签、标题、描述，以及任意自定义字段（如 `--set customfield_10001="值"`）。

```bash
# 例 1：单条改截止日期（最常见）
python3 <工程根>/scripts/jira_cli.py --source <源名> update --preview \
  --key XMKFB-123 \
  --set duedate=明天

# 例 2：批量改状态（多个 --key；两条及以上必须带 --complete-set）
python3 <工程根>/scripts/jira_cli.py --source <源名> update --preview \
  --key XMKFB-123 --key XMKFB-124 --key XMKFB-125 \
  --status 完成 --complete-set

# 例 3：混合改（同一条单一次把字段和状态都改了，字段先写、状态后推，任一步失败整条记失败）
python3 <工程根>/scripts/jira_cli.py --source <源名> update --preview \
  --key XMKFB-123 \
  --set duedate=2026-08-20 --set priority=高 --set labels='["线上问题","需回归"]' \
  --status 完成

# 例 4：改标题 / 描述（正文字段只允许单条，禁止进批量）
python3 <工程根>/scripts/jira_cli.py --source <源名> update --preview \
  --key XMKFB-123 \
  --set summary="新标题" \
  --description-file /tmp/desc.md --description-format md
```

## 四、`update` 参数速查

| 参数 | 说明 |
|---|---|
| `--key` | 可重复，一次一个单号，批量就重复写。**没有** `--keys` 逗号分隔、**不能**从文件读清单、**不接受** JQL 当批量入口 |
| `--set 字段名=值` | 可重复。键只认 Jira 英文字段名：`duedate` / `assignee` / `priority` / `fixVersions` / `labels` / `summary`（`description` 走 `--description-file`） |
| `--status 目标状态` | 独立于 `--set`。**禁止** `--set status=` 或 `--set 状态=`（会被拒）。目标状态按用户所说的原文匹配——Jira2 实测完成类状态显示名就是「完成」，用户说「完成」即直接匹配「完成」，不再做任何映射 |
| `--complete-set` | 布尔开关，去重后两条及以上时必须带。含义是「本清单就是完整集合，不是被截断的查询结果」 |
| `--allow-closed-transition` | 只有当用户明确说了「这单已关闭、还是要推」时才加。没加就碰已完成类状态的单，会整份预览被拒 |
| `--config` / `--source` | 主解析器参数，必须写在 `update` 之前 |

`--set` 的值写**人能读的值**（`--set assignee=张三`、`--set priority=高`），不要塞接口请求体（`{"name":"x"}`、`[{"id":"10100"}]` 会被拒）。

`--set duedate=` 支持一个封闭的相对日期词表：`今天` / `明天` / `后天` / `本周三` / `下周三` / `月底` / `3天后` / `2026-08-20`。词表之外一律报错，**不要自己发明说法**，拿不准就写绝对日期。

`--complete-set` 只是留痕与强制表态，**它拦不住你**，所以下面的模型层规则必须自己守住。

## 五、模型层规则（八条硬规则）

每一条都不许自行放宽。

**1. 预览文本必须原样整段粘贴给用户。**

不得摘要、改写、省略、折叠，也不得只报条数。预览里的逐条单号、旧值到新值的对照、自动填充标注、通知条数、有效期，都是给用户做决策用的——少一行就是替用户做了决定。

**2. 执行后必须原样整段粘贴结果文本；有失败条目时绝对不许说「已全部完成」。**

`apply` 整批跑完退出码恒为 0、`ok` 恒为 `true`，**退出码 0 不等于全部成功**。逐条成败只看 `counts` 与 `has_failures`。

结果里标了半成品记号的条目要单独点出来——那种条目是字段已经改了、状态卡在半路，工具不会替你改回去。

**3. 上一步查询结果 `truncated: true` 时，禁止发起批量 update。**

先让用户把筛选条件收窄到一次能看全，再改。命令行是无状态的、看不见你上一步查了什么，这条只有你能守。

**4. 标签与修复版本是整体覆盖，不是追加。**

用户说「加一个标签」「再加个修复版本」时，必须先读当前值、把合并后的完整清单提交。只传新增项会把原有的全部清掉。

正确做法：先 `get` 读出当前 labels，拼上新标签，再 `--set labels='["旧1","旧2","新"]'`。

预览会把「将被移除：xxx」列出来，贴给用户时别漏掉这行。

**5. 对陌生项目先单条试跑一次再批量。**

不同项目的工作流拓扑、状态显示名、必填项都不一样。先拿一条把路走通，再放开批量。

**6. 批量 update 的命令超时设到 600000 毫秒。**

沿用 `count-by` 设 180 秒的既有先例。50 条批量约 100 到 250 次请求，用默认 120 秒必被杀。进程被杀时 plan 已经被一次性消费掉了，只能靠 `state/audit.log` 还原进度、拿 `resume_keys` 重走。

**7. 超过 20 条建议先跟用户说一句「要不要分批」。**

这是软提示不是强制关卡——上限仍是 50 条，用户坚持一次跑完就照办。

**8. 写操作永远不得进权限白名单。**

`update`（含 `--preview`）与 `create`（含 `--preview`）、`apply`、`watch` 同口径，**永远不得写进 `.claude/settings.json` 的 `permissions.allow`**。它们都会写进 `state/plans` 或改动真实数据，每次都必须弹确认。谁也不许以「提效」为由给它们免确认。

## 六、双源写支持

写能力已对配置中的 **`Jira1`（非涉密）** 与 **`Jira2`（涉密）** 全面开放。

目标源根据《选哪个 Jira 源（每次操作前必做）》进行判定，操作命令必须显式指定 `--source <源名>`（例如 `--source Jira1` 或 `--source Jira2`），两阶段确认中的第一行会清晰回显目标源。两个源完全隔离，一次操作只作用于一个源。
