# Jira Operations

## 用途

从本机配置的多个 Jira 源实时查询单据，或在用户确认后进行全功能写操作（建主单、建子任务、改单、流转、评论、分配、关联、工时、附件、删除，以及通过 `api` 通用接口调用全量 Jira REST 接口）。入口是本技能目录下的 `scripts/jira_cli.py`，纯 Python3 标准库实现、无需安装依赖、完全不依赖任何浏览器，输出恒为单个 JSON 对象。

## 选哪个 Jira 源（每次操作前必做）

本机配置了多个 Jira 源。一次操作只作用于一个源，永远不跨源。
执行 `jira_cli.py` 的**任何**子命令（含将来新增的子命令）之前，先做完本节判定；本节优先于下面所有章节。

**准备（本次对话只做一次）**：Read 配置文件（路径见本文件「配置文件」一节），记住每个源的
`name` / `routing_business_tag` / `routing_business_desc` / `routing_project_keys`。
这个文件**只读不写**，任何情况下都不要修改它。
读不到、不是合法 JSON、或缺 `sources` 数组 → 停手报「配置不可读」，
**不猜源、不落 `default_source`、不发任何命令**。
上下文被压缩后不确定配置内容时，重新 Read，不凭印象作答。
账号、口令、Basic Auth 串不得出现在任何回答里。

**通用匹配规则**（四级都适用）：一律**最长匹配**。「涉密」是「非涉密」的一部分，
请求里出现「非涉密」只命中标签为「非涉密」的源，不得同时算命中「涉密」源；源名同理（`Jira1` 不命中 `Jira10`）。
「主 Jira」「主源」「默认源」「老地方」一律**不认作点名**、也不映射到任何源，按未点名继续往下判。

**判定顺序**：第 1→4 级依次判，统一按这一句执行——
**本级唯一命中一个源 → 定源，立即停止判定；本级零命中或命中两个及以上 → 本级判不出，进入下一级；
四级走完仍未定源 → 停下来问用户。**
唯一例外：第 1 级中用户写出了配置里**不存在**的源名时，直接跳到提问，不再往下判。

1. **点名**：用户明确指出要用哪个源——写出了某个源的 `name`（大小写不敏感），或用业务标签指源
   （「涉密那个源」「非涉密那边」）。同时指向两个源 → 判不出，进第 2 级。
   写出的源名不在配置里（如「用 Jira3」）→ 不猜、不模糊匹配，直接提问。
2. **业务标签**：请求里出现某个源 `routing_business_tag` 的字面词，但没有指源意图（如「涉密项目进度怎么样」）。
   `routing_business_desc` **不参与任何匹配**，不做近义词或语义联想。
3. **项目 key**：取 issue 编号（`ABC-123`）横线前那段、或用户直接说出的项目 key，
   **统一转大写**后与各源 `routing_project_keys` 比对。
4. **会话粘性**（两层，项目级优先）：
   4a. 本次请求能取到项目 key，且本次对话里用户曾为该 key 选定/点名过某个源，
       或助手曾用某个源对该 key 发出命令且脚本返回 `ok: true` → 用那个源。
   4b. **仅当本次请求完全不含任何项目 key 时**，用本次对话最近一次 `ok: true` 操作的源；
       但若本次请求出现了业务标签词且与该源标签不同 → 不继承，转提问。
       请求含 key 而 4a 无对应记忆时，**跳过 4b 直接提问**。
   用户点名换源即覆盖对应记忆（带 key 覆盖该 key 的槽，不带 key 覆盖最近一次）。
   记忆只在本次对话内有效，新对话从零开始。**不确定有没有记忆 → 按没有处理**（多问一句是安全的，猜错源不是）。

**字段缺失**：只要**参与判定的任一源**缺该级所需字段（第 2 级看 `routing_business_tag`、
第 3 级看 `routing_project_keys`）或其值为空 → 该级对本次判定**整体不生效**，直接进下一级，
**绝不据此排除任何源**；并在回答末尾附一句「配置里 X 缺 Y，源判定第 N 级本次整级失效，建议补上」。
提示归提示，**不要替用户改配置文件**。

**四级都没判出 → 停下来问用户**，本次不执行任何命令。按下面格式列出配置里的**全部**源
（源名与标签一律现读配置生成，**不要照抄下面的示例值**）；不带地址、不带凭据、不说明卡在第几级：

```
这次操作用哪一个 Jira 源，请选一个：
- Jira1（非涉密）
- Jira2（涉密）
```

**判出后**：命令必须显式写 `--source <源名>`，源名逐字复制配置里的 `name`（大小写敏感）；
参数位置见下方《工作流》的「参数位置硬规则」。**唯一豁免是 `apply`**——它的源在 preview 生成 plan 时
已锁死（存在 `state/plans/<plan_id>.json` 的 `source` 字段），`--source` 不生效，**不要传**。
`default_source` 只是「没人指定时的退路」，**不代表本次的正确源**，正常路径永不依赖它。

**回显**：每段结果的**正文最前面单独一行**写 `源名（业务标签）`，中文全角括号，例：`Jira1（非涉密）`。
成功、失败都要写。业务标签只能从配置读——命令输出里没有这个字段；命令**失败**时输出里连 `source` 都没有，
回显的源名一律取本次判定结果（就是你自己写进 `--source` 的那个），不要去输出里找。
缺 `routing_business_tag` 时写成 `Jira1（业务标签缺失）`。正在问用户选源时没有实际所用源，不写回显。

**创建 issue**：与查询走**完全相同**的四级判定，含第 4 级。预览的**第一行**必须是
`目标源：源名（业务标签）`，排在项目、类型、标题之前；目标源不得由 `default_source` 兜出。
执行 `apply` 之前，先只读 `state/plans/<plan_id>.json` 的 `source` 字段与预览里那行核对，
不一致就停手重做预览。用户答「确认」即执行，不必复述源名。

**「两边都查」/ 逐源自检**：拆成多次独立操作，按配置 `sources` 数组顺序依次执行，各自回显、各自呈现结果，
**不合并成一张表、不合并计数、不跨源去重或排序**；拆分后每次各自遵守既有 `--limit` 纪律，不因为要对比而放大 limit。
「我有哪些 Jira 源」这类纯配置问题，直接依据配置作答（只给源名与业务标签），**不发命令、不提问**。

**选中的源连不上**：一律停手，只如实报该源的错误码与原因，**不改用另一个源，也不问「要不要改查另一个」**。
多个源都连不上时逐个如实报错，不做任何合并推断。

## 工作流

### 最短流程

1. **定源**：按上一节判完四级。判不出就停下问用户，本次不发命令。
2. **发命令**：`python3 <本技能目录>/scripts/jira_cli.py --source <源名> <子命令> [参数]`，必须使用绝对路径调用。查询类直接发；写操作类（建单、子任务、评论、分配、关联、工时、附件、删除、修改流转，以及 `api` 通用写操作）必须先带 `--preview`，经用户确认后执行 `apply`。详见 `references/更新操作规则.md`。
3. **读结果**：只依据脚本返回的 JSON 作答。失败时按 `references/错误码处置.md` 处置。
4. **回显**：每段结果第一行写 `源名（业务标签）`，成功失败都要写。

> **参数与路径硬规则**：
> - 必须使用本地绝对路径调用脚本，例如 `python3 /Users/zhaoqing/trs/trsai-skills/skills/jira-operations/scripts/jira_cli.py --source Jira1 whoami`（实际执行时根据当前加载的 skill 目录确定）。
> - `--config` 与 `--source` 都是**主解析器参数，必须写在子命令之前**。写成 `jira_cli.py whoami --source Jira1` 会直接报参数错误。正确写法是 `jira_cli.py --source Jira1 whoami`。

各子命令的完整形态与查询纪律见 `references/命令速查.md`。

### 回答格式

列表类一律用表格呈现，列固定为：**编号、标题、截止时间、处理人、是否子任务、关联父任务**。为此 `search` 列表查询要追加 `--fields issuetype,parent`（默认输出不含这两个字段）；是否子任务看 `issuetype.subtask`（true 写「是」，false 写「否」），关联父任务取 `parent.key`（无父单写「—」），截止时间无值写「—」，处理人未分配写「未分配」。编号列用 Markdown 链接附上 issue 地址。条数多时先给前几条并说明总数与是否截断。详情类另加创建人、创建与更新时间、描述，描述为空写「无描述」。建单成功后给出新 key 与链接。不要把原始 JSON 甩给用户。

## 全局安全边界

- 配置文件**只读不写**。要改就告诉用户改哪几行，由他动手。
- 账号、口令、Basic Auth 串不得出现在回答里；列源时不带地址。
- 建单与改单必须两阶段：预览 → 原样整段贴给用户 → 用户明确确认 → 执行。**绝不连着跑完**，本工具不提供撤销。
- **标签与修复版本是整体覆盖，不是追加。** 「加一个标签」要先读旧值拼成完整清单，只传新增项会清空原有。
- 有失败条目时绝对不许说「已全部完成」，退出码 0 不等于逐条都成功。
- 上一步查询结果被截断时，禁止发起批量改单。
- 选中的源连不上就停手报错，**不改用另一个源**——两个源有同名项目 key，改源会拿另一个库的同号单当答案。
- 写操作永远不得写进 `.claude/settings.json` 的 `permissions.allow`。

**建单或改单之前必须先读 `references/更新操作规则.md`**，上面几条是最要命的，不是全部。

## 违反字面即违反精神

这些规则不接受「精神上等价」的变通。说「等用户确认」就是等用户确认，不是「我自己看过预览就算确认」。

冒出下面任何一句，说明你正在合理化。**立刻停下，先读 `references/验证与维护.md` 的「合理化对照表」再决定。** 表里每句都是模型真实说过的原话，不是假想。

## 遗留脚本禁用清单

`scripts/jira_query.sh` 与 `scripts/jira_notify_check.sh` 是遗留旧脚本，走已废弃的旧配置格式，**本技能内一律不得调用**。搜索脚本时命中它们，直接忽略。

## 配置文件

默认配置文件位于本技能目录下的：

```text
<本技能目录>/jira_config.json
```
（本地绝对路径示例：`/Users/zhaoqing/trs/trsai-skills/skills/jira-operations/jira_config.json`）

**日常调用一律不传 `--config`** —— 脚本默认自动读取同目录下的 `jira_config.json`。需要临时换配置时才显式传，且写在子命令之前。

字段含义、三个 `routing_` 判定字段、调优参数默认值、运行产物目录见 `references/配置文件说明.md`。

## 输出与停止条件

脚本输出单个 JSON 对象：成功带 `ok: true`，失败带 `ok: false` 与 `error_code`、`error`、`hint`。退出码 0 成功、1 业务失败、2 配置或参数错误。

`search` 的 `truncated` 与 `count-by` 的 `partial` 是两个字段，**都必须声明结果不完整**。

**下列情况一律停手**，不要自行找替代路径：源判不出来（问用户）、配置读不到、选中的源连不上、账号被验证码锁定、预览有条目过不了（贴原因给用户）。

## 改动本技能后必做

改完本文或任何引用文件后，按 `references/验证与维护.md` 做两件事，不许跳过：

1. **三阶段压力测试**：先不加载本技能跑压力场景、逐字记下违规措辞，再带技能复跑确认转为合规，最后针对新借口补表并重测。**没看过模型自然失败，就不知道规则防的是不是真实的失败。**
2. **多档模型实测**：本技能支持在 Claude Code、Codex、Gemini/Antigravity 等各 AI 环境下加载，须在各档模型各跑一遍——快档看指引够不够，均衡档看流程清不清楚，强推理档看有没有冗余。
