# TRS 前端 AI 规范设计思路

## 一、建设背景

随着 AI 编程工具在前端开发中的使用频率提升，团队在效率提升的同时，也逐渐暴露出一些共性问题：

- AI 容易直接进入编码，跳过需求确认、方案判断和验证环节。
- 不同 AI 工具、不同使用者的输出风格不一致，代码组织、组件拆分、接口处理方式存在差异。
- AI 在接口字段、业务规则、设计稿文案不明确时，可能会自行猜测或临时兜底，带来隐藏风险。
- 团队已有的前端开发经验主要依赖人工口头提醒，难以稳定复用。
- AI 完成代码后，容易忽略运行时验证、空状态、loading、error、响应式、提交确认等收尾动作。

因此，需要建设一套面向 TRS 前端团队的 AI 协作规范，将团队经验沉淀为 AI 可理解、可触发、可执行的规则体系，帮助 AI 在开发过程中更稳定地遵守团队工程习惯。

## 二、建设目标

本规范的核心目标不是简单约束 AI 的回答格式，而是建立一套完整的 AI 前端开发协作机制。

主要目标包括：

1. 统一 AI 与团队成员的协作方式，降低不同工具、不同人员使用 AI 时的行为差异。
2. 将团队前端开发经验结构化沉淀，避免每次都依赖人工重复提醒。
3. 引导 AI 在编码前先判断任务性质，避免需求不清、边界不明时直接实现。
4. 强化接口、表单、样式、组件、状态管理、Git 收尾等关键场景的质量控制。
5. 建立从需求确认、实施计划、编码实现、运行验证到代码审查的闭环流程。
6. 减少 AI 自行猜测业务、重复造轮子、随意兜底、默认提交或推送等风险行为。

整体思路可以概括为：

```text
把团队前端开发标准从“人脑经验”转成“AI 可执行流程”。
```

## 三、整体设计架构

当前 TRS 前端 AI 规范采用分层设计，主要包括四个层次：

```text
常驻规则层
  ↓
场景技能层
  ↓
流程控制层
  ↓
经验沉淀层
```

### 1. 常驻规则层

常驻规则是 AI 每次启动或进入项目时都应该读取的基础规范，只保留最高优先级、所有任务都需要遵守的规则。

当前常驻规则重点解决语言和沟通一致性问题，例如：

- 所有面向用户的对话、进度更新、实施计划、设计文档、审查结论默认使用中文。
- 读取英文 Skill、插件说明或模板后，用户可见内容必须翻译或改写为中文。
- 代码标识符、文件路径、命令、包名、接口字段、错误原文可以保留英文。

该层设计原则是短小、稳定、全局生效，避免把大量细节规则塞入常驻上下文，造成 AI 每次任务都加载过多无关内容。

### 2. 场景技能层

场景技能层是本规范的核心。它将前端开发中的不同任务类型拆分成独立 Skill，让 AI 在遇到对应场景时按需加载相应规则。

当前主要 Skill 包括：

| Skill | 主要作用 |
| --- | --- |
| `trs-development-preflight` | 开发前置检查，判断任务走完整流程、轻量流程还是 Bug 修复流程 |
| `api-integration` | 约束接口封装、loading、error、empty、防重复提交等处理 |
| `css-patterns` | 约束样式、布局、响应式、z-index、UnoCSS 与 Less 使用方式 |
| `form-validation` | 约束新增、编辑、筛选、弹窗表单的校验、提交和回显 |
| `vue-component-design` | 约束 Vue 组件拆分、Props、Emits、composable 抽取 |
| `pinia-store-design` | 约束 Pinia Store 和跨组件、跨路由共享状态设计 |
| `ui-component-reuse` | 约束公共组件、页面组件、自研组件的复用和放置方式 |
| `trs-code-review` | 约束代码审查、提交前检查、GitLab MR 检查和验收检查 |
| `jira-git-workflow` | 约束 Jira 任务完成后的 commit 信息、提交和推送确认 |
| `git-tag-release` | 约束 tag、发版和版本号处理 |

这种拆分方式避免了单个大文档难维护、难触发、难执行的问题，也方便后续按领域持续补充。

### 3. 流程控制层

流程控制层用于解决 AI 容易“直接写代码”的问题。

当用户提出开发类需求时，AI 不应只根据改动大小判断是否直接实现，而应先根据任务性质进行分流：

#### 完整流程

适用于：

- 新功能、新页面、新模块。
- 业务交互或业务流程变化。
- 接口联调、请求参数、响应结构变化。
- 新增或编辑表单。
- 权限、登录态、用户信息、跨页面状态。
- Store 设计、组件拆分、组件重构。
- 影响验收边界的业务重构。

推荐流程：

```text
开发前置检查
  → 需求确认
  → 实施计划
  → 编码实现
  → 浏览器运行时验证
  → 代码审查
  → 询问是否提交
```

#### 轻量流程

适用于：

- 纯样式微调。
- 文案调整。
- 静态展示字段调整。
- 图标替换。
- 纯文档、纯类型、纯配置、纯脚本变更。

轻量流程不强制完整需求确认和实施计划，但仍需要按相关 Skill 的关键规则执行，并完成针对性验证。

#### Bug 修复流程

适用于：

- 明确报错。
- 页面异常。
- 样式错位。
- 接口异常。
- 状态异常。
- 交互失效。

Bug 修复不应直接猜测修复，而应先定位根因，再做最小修复和验证。如果排查发现实际是需求变化或业务规则调整，需要重新回到开发前置检查流程。

### 4. 经验沉淀层

经验沉淀层用于记录团队在真实项目中反复遇到的问题，并逐步转化为可执行规则。

当前经验池中已经记录了以下典型规则：

- 无数据时不能让页面直接空白，需要展示空状态。
- 接口文档和实际返回不一致时，AI 不能擅自兜底，需要提示用户确认。
- 表格高度需要根据默认分页条数控制，不能无限撑开页面。
- 图表需要检查边距、legend、axisLabel、grid 是否遮挡。
- 页面文案、标题、tab、按钮、表格列名必须和设计稿保持一致。
- 数字格式化优先复用项目公共方法，避免页面内临时写 `toFixed` 或手动拼单位。
- 接口联调完成后，需要清理 mock 数据、硬编码、临时 `setTimeout` 和调试日志。
- commit 后不能默认 push，必须询问用户确认。

这些内容会先作为经验池集中记录，待规则稳定后，再拆分到对应 Skill 或代码审查清单中。

## 四、核心设计原则

### 1. 短规则常驻，复杂规则按需触发

常驻规则只放全局底线，复杂规则拆到 Skill 中按场景触发。

这样既能保证 AI 每次都遵守基础规范，又不会让所有任务都加载大量无关规则，降低上下文噪音。

### 2. 按开发场景拆分规范

前端开发不是单一动作，不同场景的风险点不同。

接口任务关注数据结构、loading、error、empty；表单任务关注校验、回显、提交；样式任务关注布局、响应式、遮挡；组件任务关注复用、拆分和职责边界。

因此规范按场景拆分，而不是简单按“代码规范”“提交规范”堆叠。

### 3. 流程优先于单点规则

AI 最大的风险往往不是不会写某一段代码，而是跳过关键过程。

因此规范设计中明确了开发前分流、需求确认、计划制定、运行验证、代码审查和提交确认，让 AI 的工作过程可追踪、可校验。

### 4. 业务不确定时不允许 AI 猜

对于接口字段不一致、后端漏字段、数据类型不一致、权限问题、需求边界不清等情况，AI 必须提示用户确认。

原则是：

```text
影响业务展示、计算、判断或提交的数据问题，AI 不能自己猜。
```

### 5. 优先复用项目已有资产

AI 写代码前需要先查看项目已有公共组件、公共方法、资源目录和同类页面实现。

公共组件、公共方法、样式方案、图标资源、图片资源都应优先复用，避免重复造轮子，保持项目一致性。

### 6. 建立验证闭环

开发完成后，AI 不能只说明“已完成”，还需要根据任务类型说明验证情况。

验证内容包括：

- lint。
- 类型检查。
- 单元测试。
- 页面运行验证。
- Console 错误检查。
- Network 请求检查。
- loading、empty、error 状态检查。
- 布局遮挡、溢出和响应式检查。

如果某项验证无法执行，也需要说明原因。

## 五、关键风险控制点

### 1. 需求风险

通过开发前置检查和需求确认，避免 AI 在需求不完整时直接实现。

重点控制：

- 页面范围是否明确。
- 交互流程是否明确。
- 数据来源是否明确。
- 非目标范围是否明确。
- 验收标准是否明确。

### 2. 接口风险

通过 `api-integration` 约束接口处理。

重点控制：

- 接口文档和实际返回不一致时必须确认。
- 不默认一次性请求所有 tab。
- loading 粒度应落到具体模块。
- 不滥用 `Promise.all`。
- 空数据、异常数据、请求失败需要有明确处理。

### 3. UI 风险

通过 `css-patterns`、`ui-component-reuse` 和经验池规则约束页面表现。

重点控制：

- 页面不能无数据空白。
- 表格不能无限撑开页面。
- 图表不能贴边或遮挡。
- 文案必须和设计稿一致。
- 图片、SVG 资源目录和命名保持统一。

### 4. 代码结构风险

通过 `vue-component-design`、`pinia-store-design` 和 `ui-component-reuse` 控制实现结构。

重点控制：

- 不随意新建重复组件。
- 不把页面临时逻辑抽成不必要的公共方法。
- 跨组件状态需要判断是否使用 Pinia。
- 组件 Props、Emits、composable 职责边界清晰。

### 5. 收尾风险

通过 `trs-code-review`、`jira-git-workflow` 和 `git-tag-release` 控制任务收尾。

重点控制：

- 提交前先审查。
- commit 信息符合团队规范。
- commit 后不默认 push。
- 发版和 tag 操作需要按规范执行。
- 未经用户确认不得提交、推送或创建 MR。

## 六、落地方式

当前规范主要通过以下方式落地：

1. 在 AI 工具中配置团队常驻规则，保证基础沟通和行为一致。
2. 按开发场景维护独立能力模块，让 AI 在不同任务中加载对应规则。
3. 通过流程文档沉淀开发步骤、评审要求和经验池。
4. 对可自动化的检查和收尾动作，逐步使用脚本或工具辅助完成。
5. 支持在不同 AI 工具中复用同一套规范，减少多工具使用时的标准差异。

落地后，团队成员在业务项目中使用 AI 时，AI 可以先遵守统一基础规则，再根据具体任务触发对应场景规范，从而按照团队统一标准工作。

## 七、后续演进方向

后续可以从以下几个方向继续完善：

1. 将经验池中已经稳定的规则，逐步沉淀到对应场景能力中。
2. 补齐项目级公共方法说明，例如数字格式化、金额格式化、空值处理、时间格式化等工具函数的具体名称和用法。
3. 补齐项目级空状态组件、表格组件、图表组件、公共筛选组件等组件使用规范。
4. 持续完善代码审查清单，把真实项目中发现的问题沉淀为检查项。
5. 增加更多自动化脚本，例如组件复用扫描、mock 数据清理检查、资源目录检查等。
6. 根据不同业务项目的特点，允许各项目补充自身的项目级约束。
7. 定期复盘 AI 输出问题，将高频问题转化为规则、Skill 或脚本。

## 八、总结

TRS 前端 AI 规范的设计重点，不是单纯告诉 AI “代码应该怎么写”，而是让 AI 按团队真实开发流程工作。

这套规范通过常驻规则保证基础一致性，通过场景 Skill 保证专业约束，通过流程分流控制任务节奏，通过经验池持续沉淀团队实践，通过验证和审查机制保证最终交付质量。

最终目标是让 AI 从一个临时编码助手，逐步变成符合 TRS 前端团队工程习惯的协作成员。
